# Pro AX630C 视频流水线

`ax630c.so` 从 `open_vin_capture` 读取 YUYV，优先把已出队的 capture DMA 缓冲区导入 VC8000E；导入失败才复制到编码器帧缓冲。Core 使用绑定编码器接口读取 H.264 AU。

## 本地 RGB 显示

`source_display` 从 YUYV 采集缓冲生成 640×360 RGB565，小屏通过 `video=display` 的共享内存环读取，不经过 JPEG 或 H.264 解码。有编码消费者时复用编码前的 RGB 缓存；仅有小屏消费者时直接出队 VIN 缓冲，跳过已完成的旧帧，复制最新画面后立即归还缓冲。Core 的 display-only 需求只保持采集绑定，不调用编码器读包，后端不能依赖编码路径产生 RGB。画面等比缩放、空余区域留黑；进入无信号模式时预先转换同一份已批准的占位源图，后续 RGB 请求可独立读取。

显示缓存使用独立锁及单调时钟条件变量；直接出队与模式切换、编码共用 VIN 锁，单次采集轮询最多 50 ms，其余等待释放 VIN 锁。只有最近两秒内有显示请求时才转换实时帧，最多 15 fps；关闭小屏串流后沿用 Core 的消费者需求机制释放采集与编码资源。显示等待最多一秒，返回 timeout 时客户端保留上一帧；重新连接仍请求 RGB，不永久回退编码流。

仅小屏采集连续 300 ms 没有 VIN 帧时，若桥片仍发布与当前采集一致的稳定尺寸，重建 DMA 队列并重新导入编码器缓冲。失锁或几何变化期间等待绑定流程处理，不反复重开旧尺寸。这与编码读取路径的停帧恢复对应，避免低分辨率切换后只有 RGB 消费者时永久停帧。

## 按需采集与空闲时钟

沿用 Core 的消费者需求判断：网页、VNC/RTSP、录制或其他实际取帧需求结束后解绑视频源。创建编码器只保存配置；绑定时才打开 `/dev/es_venc`、映射命令池并申请帧缓冲。解绑依次停止采集、释放 DMA 导入及编码缓冲、解除映射、关闭编码设备；再次绑定从新 IDR 开始。

`open_vin_capture` 在 STREAMON 前取得 runtime PM 引用，STREAMOFF 停止 SIF/WDMA/CSI 并排空中断和 AXI 请求。空闲 1 秒后关闭 ISP 内部 gates 及 VI/ISP_MM 公共时钟；AXI 仍忙时拒绝关钟。快速重开即使取消了 autosuspend，也要重新放行 AXI。恢复只开时钟并恢复请求，不重复全局 reset 扫描。CSI 停流继续关闭 D-PHY 和自身时钟；空闲状态查询只返回缓存计数，不读已关钟的寄存器。

VCMD 同时持有文件生命周期和命令引用，覆盖 ioctl、映射及最终关闭的 abort/寄存器访问，最后关闭后空闲 1 秒再关 VENC 时钟。关闭异常且 DMA 未确认停止时保留供电。诊断用 JENC/VDEC 驱动只在读取寄存器或改频率时唤醒，并在空闲 1 秒后关钟。所有模块保留 reset 状态，不逐帧切换时钟。

HDMI 输入经 LT86102UXE 分配到 HDMI OUT 和 LT6911UXC 采集桥。空闲策略只管理 SoC 采集/编码侧，不切换 `/proc/lt6911_info/{power,hdmi_power,loopout_power}`，保留桥片 EDID/HPD 和持续环出。不能用移除 `clk_ignore_unused` 代替驱动的资源管理。

## 无信号占位

无信号画面在后端编码，前端控制台不叠 Vue 占位图。画面资源来自 `onekvm-video-soph-mmf/src/no_signal_frames.inc`，同步复制到本目录的 `src/no_signal_frames.inc`；更新 MMF 已批准的 PNG 后必须重新同步该文件。`ax_no_signal.c` 把 packed NV21 解包并转为 VC8000E 输入所需的 YUYV，尺寸不匹配时等比留黑边。

首次绑定而 HDMI 未锁定时，后端分配默认 1920×1080 编码帧缓冲，把占位图写进其输入区，并以 5 fps 经正常 VC8000E 通道输出 H.264。实时输入消失后，从首次检测到无信号起等待 3.2 秒，再停 VIN 并切换占位；即使 VIN 仍输出旧帧，也不能用这些帧重置无信号计时。105 的常规模式切换在此窗口内恢复，避免向浏览器连续发送占位与新尺寸两个 IDR、引起额外解码停顿。真实断信号实测从关闭 HDMI 到占位 IDR 约 4.5 秒。已知无 HDMI 时不得反复重建 DMA 环。两种画面切换时都重新从 IDR 开始，使 WebRTC 及录制端可解码。

`/proc/lt6911_info/hdmi_rx_status` 只表示插头存在。判定锁定还要确认桥接芯片电源为 `on`、`status` 为 `new res` 或 `stable`，且宽、高、帧率均非零。占位期间每次编码前重新检查输入，信号恢复后启动 VIN 并切回实时帧。

`ax630c-once` 属于单独的 `onekvm-video-ax630c-diag` 包，可在独占编码器的条件下验证完整 H.264 输出。不要在 Core 正在采集时运行它。

## 输入模式切换

以 139 的运行时重开流程为参照，先分清「获知 HDMI 新尺寸」和「CSI 已有可采集像素」：

| 设备 | 运行时流程 | 可以重开采集的时刻 |
| --- | --- | --- |
| 139 · PicoKVM | TC358743 `SOURCE_CHANGE` → 停 CIF、释放缓冲 → `QUERY_DV_TIMINGS` 确认新时序 → 按新尺寸开流 | 查询返回稳定时序后 |
| 105 · Pro Desk | LT6911UXC 失锁 → 确认断信号后停 VIN → 等桥片发布新 CSI 尺寸 → 释放缓冲并按新尺寸开流 | CSI 已输出新尺寸后；输出尺寸未变则保留编码器 |

105 原始桥片固件的 HDMI 接收侧约 0.9 秒就能读到新尺寸，但 CSI 要约 2.7–2.9 秒才输出有效像素；139 的 `QUERY_DV_TIMINGS` 没有这段等待。105 已按 139 的「停旧采集、等新时序、重开采集」顺序运行；提前停 VIN、读取 HDMI 接收侧尺寸或提前武装 CSI 均未缩短这段等待。不能用尚未可采集的 HDMI 尺寸宣称切换完成。后续已定位并缩短桥片固件中的等待，见下一节；下文保留此前对照数据和已撤回实验。

### 105 桥片固件的等待

原始 LT6911UXC 固件在低于 50 MHz 像素时钟时额外等待 500 单位，并在 PLL 与 CSI 初始化周围还有独立的固定等待。用户授权写入后，按 NOR 只能清位的方向分八档试验；每档写前和写后均整片回读 128 KiB，并逐档验证四角、八色条、输入及编码尺寸。当前 105 为第八档，整片 SHA-256 `714549206422f9cc1d87bb0eee07183dedea98d94ea5b0219122c578e83f4fb0`；写入和验证见[第八档报告](../../../artifacts/firmware/105-lt6911uxc-stage8-20260928.md)，原始备份及前七档见[固件实验记录](../../../artifacts/firmware/105-lt6911uxc-low-clock-20260928.md)。

同一分屏器、同一输入模式、浏览器逐帧测量下，105 原始固件最低三档首帧中位数 3170 ms，第七档为 2239 ms。第五、第六、第七档十二档输入对照中，105 中位数分别为 2241、2188、2203 ms，三台每档均正确。当前第八档在六轮十二档测试中，105／107／139 首帧总中位数为 1990.5／1828／2135.5 ms；六轮各自的排序均为 107、105、139，三台各 72/72 档图案和尺寸正确。105 在 50/72 档快于 139，仍有单档反例；第八档相对第七档的独立收益小于跨轮波动。105 的五档输出缩放和持续断信号后的占位／恢复均通过。不能据此宣称每种模式都已稳定快于 139；逐档报告及哈希见上述固件文档。

第七档再测最低三档时，105 桥片约在 `xrandr` 开始后 2065、1968、2026 ms 才发布可采集 CSI 新尺寸，网页首个正确帧再分别增加 359、264、89 ms；两端时钟均已 NTP 同步。105 与 139 同源最低六档均 6/6 正确，网页首帧中位数为 2196.5／2099.5 ms。当前主等待仍在 LT6911UXC 输出 CSI 像素之前，不能凭缩短后端轮询宣称追上 139；证据见固件记录中的阶段事件和逐帧报告。

独占 VIN 的新证据修正了「发布尺寸前绝无正确帧」这一更强说法：先显示目标图案，约在模式命令开始后 1.05 秒按已知目标尺寸预开 VIN，720×400、640×480、720×480 的首个正确 YUYV 帧分别比内核 `new res` 发布时间早 146、132、151 ms。桥片 HDMI 接收侧可更早取得尺寸；提前开流不会消去桥片内部锁定等待，只能回收发布与首帧之间的一部分时间。

105 实机上的 `0xd2:8b/96` 始终返回 `0×0`。受驱动 `chip_lock` 保护的只读 `/proc/lt6911_info/rx_geometry` 改读 `0x86:80` 半宽、`0x86:7e` 高；640×480→720×480 时，该尺寸比正式 `new res` 早 836 ms。接收侧也可能短暂报告 `800×442` 这类中间值，因此后端仅在旧 VIN 停帧后两次确认，并以正式发布的新尺寸纠正预开的候选。已预开但尚无真实 VIN 帧时，正式尺寸一发布就重开 DMA 环；收到真实帧后不再重复开环。正常 Core 路径从最低模式逐档测到 1920×1080，105／139 各 12/12 通过四角、色条、输入和编码尺寸检查；网页首帧中位数为 2126／2034 ms。105 五档输出缩放 5/5，断信号占位及恢复通过。105 仍未稳定快于 139；实测及当前部署见 [`105 提前采集验证`](../../../artifacts/video/105-early-rx-validation-20260928.md)。
